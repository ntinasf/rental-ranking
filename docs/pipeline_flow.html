rental-ranking · data-flow reference

Raw to Ranked

How three Inside Airbnb snapshots become the 44,684 × 66 matrix LightGBM will train on: every module on the path, the gates that guard it, and the numbers that changed along the way. The target is a demand proxy — forward availability, never "bookings".

rebuild = shipped parquet, byte-identical 44,684 listings · 61 features · 393 query groups asset features:2026.08.17
layer 1

Snapshots to the processed parquets

One orchestrator chains three pure transforms per city and entity, runs the checks no single frame can see, and is the only code that writes data/processed/. Preprocessing is lossless: apart from de-duplicating listing ids, every suspicious value is warned about once, with a count, and kept.

layer 2

Processed parquets to the feature matrix

The second orchestrator mirrors the first: pure transforms, chained in an order that is part of the contract, with the filesystem touched only at the very end. Row count changes exactly once — at the filters — and every quantile downstream of them is computed on the population that will actually be ranked.

the matrix

What the 66 columns are

Three roles, kept apart on purpose: identifiers join and group, targets are trained against, everything else is an input. feature_columns() is the only sanctioned way to read the feature list.

3 identifiers — id · query_group · cluster_id 2 targets — grade · blocked_fraction_90 11 structural 10 host 20 amenity 14 review 3 neighbourhood 3 spatial

Nothing in the feature block is imputed — price is the project's sole imputed column, filled upstream for a reason that does not generalise. Nulls that remain are honest: review cohort 16.3 %, bedrooms 7.5 %, beds 3.7 %, bathrooms_shared 0.1 %, one lone-neighbourhood row. Group-key columns (city, room_type) ride along as conditioners — constant inside a group, they can separate no pair.
